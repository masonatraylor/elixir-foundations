Elixir Foundational Knowledge Guide

Welcome to Elixir! Elixir is a dynamic, functional language designed for building scalable and maintainable applications. It leverages the Erlang VM (BEAM), known for running low-latency, distributed, and fault-tolerant systems.

This guide covers the essential concepts needed to read, write, and understand Elixir code.

1. Functional Programming Basics

Elixir is deeply functional. Data is immutable and state is never mutated directly; instead, functions return new copies of data.

Immutability

When you "modify" a data structure, Elixir returns a new data structure under the hood, sharing as much memory as possible with the old one (structural sharing).

# 'list' remains [1, 2, 3]
list = [1, 2, 3]
new_list = [0 | list] # [0, 1, 2, 3]

The Pipe Operator (|>)

One of Elixir's most famous features is the pipe operator. It passes the result of the expression on its left as the first argument to the function call on its right.

# Instead of this nested mess:
String.upcase(String.trim("  hello  "))

# We do this:
"  hello  "
|> String.trim()
|> String.upcase()
# => "HELLO"

2. Pattern Matching

In Elixir, = is not just an assignment operator; it's a match operator. It tries to make the left side match the right side.

# Basic match
x = 1

# Destructuring a Tuple
{:ok, result} = {:ok, "success"}
# result is now "success"

# This will raise a MatchError because :error does not match :ok
{:ok, result} = {:error, "failed"}

Pattern Matching in Functions

Elixir allows you to define the same function multiple times with different patterns (Function Clauses). It executes the first one that matches the arguments.

def handle_response({:ok, body}) do
  IO.puts("Success: #{body}")
end

def handle_response({:error, reason}) do
  IO.puts("Failed: #{reason}")
end

3. Concurrency (The Actor Model)

Elixir's concurrency is based on the Actor Model. All code runs inside lightweight threads called processes (not OS processes). Processes are isolated, run concurrently, and communicate via message passing.

# Spawning a new process
pid = spawn(fn -> 
  receive do
    # Include self() in the reply so the receiver knows who sent it
    {:ping, sender} -> send(sender, {:pong, self()})
  end
end)

# Sending a message
send(pid, {:ping, self()})

# Receiving a message
receive do
  {:pong, ^pid} -> IO.puts("Got pong from the exact process we expected!")
after
  1000 -> IO.puts("Timeout!")
end

4. OTP (Open Telecom Platform)

While spawn, send, and receive are powerful, managing state, errors, and process lifecycles manually is tedious. OTP is a set of abstractions that handle this for you.

GenServer (Generic Server)

A GenServer is a behavior module for implementing the server of a client-server relation. It's the standard way to maintain state and handle asynchronous/synchronous operations.

Crucially, GenServers do not mutate state. Under the hood, a GenServer is an infinite recursive loop. When a callback returns a new state, that state is passed as an argument to the next iteration of the loop.

  • init/1: Sets the initial state.
  • handle_call/3: Synchronous requests. Returns {:reply, response, new_state}.
  • handle_cast/2: Asynchronous requests (fire and forget). Returns {:noreply, new_state}.
  • handle_info/2: Handles messages sent directly via send/2.

Supervisors

Elixir embraces the "let it crash" philosophy. Instead of defensive programming (catching every possible exception), we let processes crash and have Supervisors restart them in a known good state.

children = [
  # Starts the Worker module
  {Worker, initial_state}
]

# The Supervisor will restart the Worker if it crashes
Supervisor.start_link(children, strategy: :one_for_one)

5. Mix and ExUnit

  • Mix is Elixir's build tool. It creates projects (mix new), manages dependencies, compiles code, and runs tests.
  • ExUnit is the built-in test framework. It uses macros (like assert) to write clean, concurrent tests.
